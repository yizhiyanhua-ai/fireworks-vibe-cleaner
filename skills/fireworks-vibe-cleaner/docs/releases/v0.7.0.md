# v0.7.0 — Plan refresh, canary-gated cleanup and real execution evidence

The first approved real cleanup showed that the low-level archive executor was sound, while orchestration still relied on task-specific scripts. This release moves those repeated safety steps into the product.

- `archive-refresh` revalidates every source identity, source hash, archive hash and selected member byte in an expired unexecuted plan. It preserves the old plan, records the superseded hash and creates a new hash that requires human approval.
- `archive-workflow-plan` binds exactly one canary plan to a disjoint cleanup plan. `archive-workflow-apply` enforces canary removal verification, original-path restoration verification, cleanup removal and final verification in that order. Any failed canary state blocks cleanup. Existing journals cannot be replayed.
- `archive-verify --summary` and `archive-workflow-verify` provide compact machine-readable receipts without hiding whether native continuation remains unverified.
- Archive removal now records one free-space observation per filesystem device with start/end timestamps. Logical bytes and observed volume movement remain separate.

The sanitized real operation on 2026-09-23 covered a 2,036,098-byte restore canary and 188 cleanup originals totaling 6,280,929,947 logical bytes. All 188 ended in valid archive-only state and nine archives remained verified. The executor and external `df` windows observed different free-space deltas because their time windows differed; neither is presented as tool-exclusive reclaim. Native conversation continuation and restoration of every removed source remain unverified.

See the bilingual README and [sanitized evidence](../experiments/real-approved-cleanup-2026-09-23.json). Private paths, session identifiers, plan hashes and archive locations are excluded.
