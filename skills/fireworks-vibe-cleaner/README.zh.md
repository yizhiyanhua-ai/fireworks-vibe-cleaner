在 Codex 或 Claude Code 里用自然语言检查日志、会话和缓存，让 Jev 辅助判断处理方式，再由你确认具体方案后执行。推荐安装后优先配置 Jev；选择纯规则模式也可继续使用。

**清理前必须人工确认具体方案。** v0.2.0 支持先校验已有归档，再移除获准处理的旧主会话原件，并可恢复到原路径。文件字节恢复不代表原生续聊已经验证。

## 在 Codex / Claude Code 里怎么用

### 1. 安装后，优先配置 Jev

> 帮我从 https://github.com/yizhiyanhua-ai/fireworks-vibe-cleaner 安装 v0.4.0，放到当前工具的个人 Skill 目录。不要覆盖已有安装，也不要清理文件。然后指导我安全配置 Jev。

需要 macOS/Linux 和 Python 3.11+，也可参考[手动安装指南](docs/cli.zh.md#安装)。Jev 使用 `TYPESAFE_API_KEY`，通过密钥管理器或进程环境安全注入，不要把 Key 粘贴到聊天、报告或命令历史。`doctor` 只检查 Key 是否存在，不代表鉴权或推理调用成功。

> 联网调用前，先说明 Jev 接收哪些信息、是否可能收费。如果我选择纯规则模式，就不配置 Key，继续本地检查。

**优先让 Jev 做快速筛选和处理建议。** 本地代码提取少量事实，Jev 批量选择“保留、待复核、备份保留原件、准备移除方案”，同时选择相应理由。备份和删除是两个独立决定；会话移除必须先验证备份，再确认具体计划。只发送类别、大小区间、保留期是否满足、保护/格式检查结果，以及你选择的目标，不发送路径、文件名、会话正文或代码。没有 Key 或调用失败时，明确显示本地复核结果，不冒充 Jev 建议。

Jev 擅长快速、明确的分类选择；容量计算、日期比较和文件校验交给代码。每批 8 个候选，最多 3 批并发；先给建议，范围确定后再做完整备份哈希校验。仅看元数据无法判断会话内容是否还有价值，旧文件、大文件都不等于无用。具体设计和边界见 [Jev 快速筛选](docs/jev.md)。

### 2. 检查空间，再看辅助建议

> 用 fireworks-vibe-cleaner 检查 Codex 和 Claude Code 的占用，列出主要来源和必须保留的内容。如果我已经授权调用，让 Jev 快速筛选候选。直接在对话里逐项列出文件、建议、为什么这样处理、备份或删除的备选方式、预计影响和还不确定的地方。先给建议，再对我选定的范围做完整校验。不要移动或删除文件。

项目根需要明确指定。扫描不代表整盘统计，跳过的目录和无法读取的文件必须说明。活跃状态未知、受保护对象和凭据，都不能通过模型建议获得删除权限。

### 3. 确认具体方案后再执行

> 给我看具体文件、处理方式、占用大小、恢复限制和计划哈希，等我确认这份方案再执行。如果要处理已经归档的会话，还要说明历史记录可能不可用，恢复文件字节不代表可以继续对话。

两种清理流程相互独立：

- **旧日志与缓存：**先批准隔离，验证后可恢复，或另行批准永久清理。同盘隔离释放 **0 字节**。
- **已经备份的主会话记录：**`archive-plan` 校验已有归档与所选源文件字节。取得具体计划批准、停止写入并明确确认历史风险后，`archive-apply` 才移除这些原件，保留归档。关联文件与 harness 索引均不修改。

“帮我清理”不代表批准未知文件。修改前必须停止相关写入；`--writers-stopped` 是确认声明，不会替你关闭进程。文件或范围变化后需要重新生成计划。

## Codex 历史会话过多时

> 用 fireworks-vibe-cleaner 检查我的 Codex 历史。索引会话总量超过 3 GiB、单个会话超过 3 GiB，或未归档数量超过 200 时，先提出处理建议。保留最新 100 个会话、最近 30 天更新的会话、置顶会话、当前会话和我指定保留的内容。先在聊天里给概览，再附完整计划链接，等我确认具体范围后再执行。

阈值可以调整，触发后**只生成建议，不自动归档或删除**。`history-audit` 以只读 SQLite 方式读取 Codex 权威索引，检查已知的置顶、父子关系字段以及有读取上限的会话头部。会话数量对应整个索引，不等于当前 UI 筛选后的列表；字节统计来自可读取的索引文件，存在未能检查的文件时只是下界，报告会说明缺口。

请求确认前，先在聊天中说明触发条件、索引及未归档数量、已计量字节与遗漏范围、保留数量、拟处理主会话及**全部受影响后代**、操作方式、恢复限制和预计回收空间，再附完整计划与哈希。不能只发文件链接让用户自行判断。

**原生归档改变历史列表的显示状态，预计释放 0 字节。** 当前支持的 Codex 0.154.0 归档 API 会连带归档后代，所以计划必须包含整个后代范围；取消归档每次只作用于一个会话，恢复时需要逐个处理受影响 ID。工具通过原生 API 操作，不直接修改索引数据库，也不手工移动会话文件。

只读检查支持具有已知 schema 的 macOS/Linux 环境。原生历史写操作首版仅支持 macOS，并要求 OS 沙箱禁止联网；不支持的原生版本或未知的置顶、父子关系状态会拒绝修改。后代中有当前、置顶或指定保留的会话时，不能通过归档父会话绕过保护。

真正回收存储空间，需要另走已有 ZIP 校验和明确批准的原件移除流程。批准调整历史列表，不代表批准删除会话原件。

初次原生验证使用隔离的合成父/子/孙会话与本机 Codex 程序，会话文件内容的 SHA-256 保持不变。这只能证明该测试中的 API 行为，不代表已归档真实用户历史，也不证明原生会话续聊成功。

索引、文件或关联关系检查不完整时，仍可报告容量与数量，但拒绝生成可执行原生归档计划。取消归档会更新 Codex 的时间字段和文件 mtime；恢复核验覆盖路径、内容和归档状态，不保证原始时间戳。

`archive-restore` 恢复原路径和精确字节，新 inode 属正常现象；它不重建索引，也不恢复完整 harness 状态。请保留归档、manifest 和事务日志。仅备份会保留原件并增加占用。

## v0.4.0：真实 Jev 筛选耗时对比

2026-09-22，使用本机 **33 个真实旧主会话文件，共 1,049,047,931 字节（约 1.05 GB）**，对同一批选项分别进行串行和并发调用。没有模拟服务商响应；调用前后完整文件哈希一致。

| 观察项 | 串行（1 批同时执行） | 并发（最多 3 批同时执行） |
| --- | ---: | ---: |
| 候选 / 实际 API 调用 | 33 / 5 | 33 / 5 |
| 本地事实检查 | 7 ms | 8 ms |
| API 总等待时间 | 10,063 ms | 3,453 ms |
| 建议阶段总耗时 | **10,070 ms** | **3,461 ms** |
| Jev 原始选择 | 33 准备移除方案 | 31 准备移除方案、2 待复核 |
| 经过低 confidence 分流后的建议 | 33 待复核 | 5 准备移除方案、28 待复核 |
| 实际删除 / 释放空间 | **0 / 0 字节** | **0 / 0 字节** |

这一次并发耗时降低约 **66%**。计时包括新鲜的本地身份/保留期/会话头检查与真实推理，复用已有选定清单；不含全盘扫描、完整备份校验及基准专用的前后源文件哈希。两轮输入共 25,628 tokens，按[官方单价](https://docs.typesafe.ai/models)估算 US$0.001076376，账单未核验。

两轮建议存在差异，低 confidence 候选按产品规则转待复核。这个样本没有标注答案，不能证明删除判断准确，也不保证每次都能达到相同提速。没有执行任何真实清理。“准备移除方案”仍需确认使用需求、核验备份和保护状态，并取得具体计划的人工批准。[脱敏结果](docs/experiments/real-jev-triage-2026-09-22.json) · [可复现实测工具](tools/live_triage_validation.py)。

## 真实 10 GiB 验证与 Jev 线上对比

以下是此前的备份实测，早于 v0.2.0 的归档移除流程与扩展 Jev 选项，不能作为这些新能力的实测结果。

**真实数据清理必须先经过人工确认，确认内容须包含具体范围和操作。** 本轮仅读取原件、创建私有归档并校验恢复字节，没有隔离、移动或删除任何原始文件。

实测日期：2026-09-21。选取 **564 个已有会话文件，共 10,932,021,589 字节（10.181 GiB）**；Codex 样本至少 7 天未修改，Claude 样本至少 1 天未修改。选择时检查了打开句柄，并冻结全文哈希。源目录盘点跳过 227 个边界，不能视为完整磁盘统计。

| Codex 历史会话 | 560 | 9,932,261,559（9.250 GiB） | 5,447,045,764（5.073 GiB） | 45.16% | 全部一致 |
